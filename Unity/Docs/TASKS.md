# Tasks — Unity migration

**This file is the only owner of migration task status.** The reference tracker `docs/PROGRESS.md` is paused and points here. One log entry per meaningful status change goes in §8.

Status values: `todo` · `in progress` · `done` · `blocked (reason)` · `human` (needs an owner verdict, never marked done by an agent). Code status, automated checks, design approval and human play are recorded separately; a passing test never closes a `human` row.

Phase rule: a phase is complete only when every non-human task in it is `done` and its playable acceptance has been run by a person and recorded. Later phases may start engineering work early only where a task's dependencies are all `done`.

Sources for every task are in [MIGRATION_MAP.md](MIGRATION_MAP.md) (system entries `S-nn`, `S-Ann`) and the specialist documents; a task cites the entries it implements rather than repeating source paths. Decisions and open questions (`U-D`, `U-M`, `U-P`, `U-Q`) are in [DECISIONS.md](DECISIONS.md).

Goal (revised 2026-09-11, U-M-22): a working Unity project that compiles cleanly with its editor tooling verified; an engine-independent simulation foundation (state, tick, commands and events, PRNG, inventory and ledger, map and movement core, save/load, timing host) with a few small checks (inventory conservation, save/load round trip, sim timing, replay consistency); the data assets the foundation and the opening need; and one visible scene with movement, one machine and an editable UI Toolkit panel. No authored world, no production chain and no complete gameplay yet: crafting and machines (B-07), power (B-09) and belts (B-10) moved into Phase C, where the opening needs them, with their IDs kept. Verification is proportionate: each subsystem's checks live on the task that ports it; broader harnesses, bots, nightly runs and soaks are deferred with explicit triggers (DEF-01–DEF-04 below, U-M-23). Exit: B-ACC passes.

Scope rule for Phase B (2026-09-11): checks are written for behaviour that exists; nothing is tested before it is built. A ported reference test that fails in Unity is investigated when it is ported, not triaged in bulk. The 146 reference test failures (318/464 on 2026-09-11) are **reported failures whose individual provenance is not established**; they are neither labelled pre-existing wholesale nor made a migration prerequisite (MIGRATION_MAP.md §1).
